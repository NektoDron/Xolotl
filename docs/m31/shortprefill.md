# Адаптивный префилл MiniMax-M3.1

Короткий новый кусок может дешевле обработать экспертов в RAM, чем передавать
их исходные веса через PCIe. Экспериментальный режим оставляет dense/attention
на GPU и выбирает CPU либо смешанное выполнение routed experts. Арифметика
декода одного токена не переключается этим режимом.

По умолчанию `M31_SHORT_PREFILL_MODE=off`; это прежний путь v8. Режимы:

| Переменная | Значение | Назначение |
|---|---|---|
| `M31_SHORT_PREFILL_MODE` | `off` / `cpu` / `hybrid` / `auto` | Политика нового куска |
| `M31_SHORT_PREFILL_MAX_N` | `1024` | Максимальный размер нового куска для новой политики |
| `M31_SHORT_PREFILL_CPU_MAX_N` | `31` | В `auto`: до этого размера CPU, затем hybrid |
| `M31_SHORT_PREFILL_MATH` | `auto` / `cuda` / `ggml` | Выбор арифметики CPU-экспертов, по умолчанию `auto` |
| `M31_SHORT_PREFILL_NVFP4_CPU` | `0` / `1` | Разрешение экспериментальной CPU-арифметики NVFP4, по умолчанию `0` |
| `M31_SHORT_PREFILL_GPU_QUANT` | `1` / `0` | Точное CUDA-квантование активаций, в Engine по умолчанию `1` при новом режиме |
| `M31_SHORT_PREFILL_GPU_OAI` | `1` / `0` | Точный CUDA OAI перед down-квантованием, требует GPU_QUANT; в Engine по умолчанию `1` |
| `M31_SHORT_PREFILL_SCHEDULE` | `dynamic` / `static` | Раздача CPU matrix tasks постоянному pool, по умолчанию `dynamic` |
| `M31_SHORT_PREFILL_SCHEDULE_CHUNK` | `4` | Размер выдаваемой группы dynamic tasks, допустимо1…64 |
| `M31_SHORT_PREFILL_PREPARED_CORRECTIONS` | `1` / `0` | Кеш поправок integer dot для повторно используемых активаций, по умолчанию `1` |
| `M31_SHORT_PREFILL_DEVICE_GATHER` | `1` / `0` | По умолчанию `1`: выборка GPU expert activation rows на GPU вместо их host-дублирования |
| `M31_SHORT_PREFILL_UPLOAD_WINDOW` | `1` / `0…16` | По умолчанию `1`; ограничение числа холодных uploads между checkpoint, `0` сохраняет прежнее планирование |
| `M31_SHORT_CPU_GBPS` | `220` | Начальная оценка пропускной способности RAM |
| `M31_SHORT_PCIE_GBPS` | `57` | Начальная оценка пропускной способности PCIe |
| `M31_SHORT_CPU_GOPS` | `6000` | Калиброванная оценка CPU arithmetic rate |
| `M31_SHORT_GPU_GOPS` | `60000` | Начальная оценка GPU arithmetic rate |
| `M31_SHORT_CPU_UNTILED_FACTOR` | `1` | Множитель цены CPU для формата без tiled kernel |

Коэффициенты определяют оценку стоимости каждой полосы. Для EPYC9654/RTX5090 измерен
отдельный профиль [`vision-shortprefill.json`](../../tools/m31/profiles/vision-shortprefill.json):
dynamic scheduling, CPU_GBPS220/CPU_GOPS6000, device gather и upload window1.
Порог и коэффициенты следует выбирать по развёртке на конкретной машине.
Политика читается при каждом новом append; calibration-процесс может
менять её без повторной загрузки весов. `n=1` и куски больше `MAX_N` используют
прежний путь. CPU-режим требует действительной RAM-арены и постоянного CPU
executor; настройки памяти/пула нужно сохранять как в принятом native profile.

`MATH=auto` учитывает действительный `gpu_experts_min_tokens` в Engine. В
принятой конфигурации порог равен32: ниже него CPU использует исходную
арифметику ggml, как CPU-ветка oracle; начиная с32 — CUDA-совместимое
квантование активаций. При `auto` ниже порога даже выбранный режим `hybrid`
переключается в CPU, чтобы сохранить этот контракт. `MATH=cuda` принудительно
выбирает CUDA-совместимый CPU executor независимо от порога; `MATH=ggml`
оставляет исходные CPU primitives и нужен для диагностики расхождения.

Это различие проверено на code128: первая версия с исходным CPU ggml на
GPU-offload batch получила top-1 78,125% и mean KL0,72914, тогда как `off`
совпал с GPU oracle побитно. CPU-ветка oracle для одиночного декода и его
GPU-ветка для префилла используют разные форматы активаций. Поэтому
побитность CPU decode не доказывает корректность batch относительно GPU.

Для IQ3_XXS/IQ4_XS новый CPU executor воспроизводит native MMQ D4: scale F32
на32 значения, целочисленный dot32, умножение на масштаб весов и затем FMA с
масштабом активаций в исходном порядке групп. AVX-512 VNNI выполняет независимые
строки параллельно, сохраняя этот порядок F32-накопления. SIMD/scalar
сверяется CPU unit test. При отсутствии нужных инструкций остаются
AVX2 либо scalar реализации того же CPU-контракта.

Принятый численный вариант выполняет квантование активаций и OAI малыми
CUDA-вызовами, а матрицы выбранных CPU-экспертов читает из RAM. Эти операции
включены в Engine по умолчанию при выборе нового режима; исходный глобальный
`MODE=off` остаётся прежним. Чистая portable CPU-квантизация оставлена для
диагностики: на реальном normalized input у неё обнаружены отличия scales
на1…3 ULP, а после CPU OAI — до6 ULP и шесть отличающихся quant values из
1572864. На многих слоях это влияет на routing и не прошло полномодельный gate.
Поэтому flags GPU_QUANT/OAI0 не являются принятой скоростной конфигурацией.

CUDA helper сохраняет собственные pinned/device buffers и заранее резервирует
ёмкость до выполнения слоёв. Ожидаемый `runtime_allocations=0` проверяется
отдельно; reserve относится к подготовке Engine, остальные copy/submit/wait/
unpack timers вложены в GPU quant wall time и CPU compute time. Формат
quantized rows сохраняется исходным; сами веса CPU-экспертов на GPU при этом
не передаются. Standalone CPU unit tests используют portable режим без GPU.

`NVFP4_CPU=0` оставляет слои с NVFP4 на native GPU целиком. Для данного
UD-IQ3_S это три routed-слоя. Их fallback не запускает спекулятивную загрузку
следующего слоя: решение для него ещё не принято. Число таких fallback
сохраняется в `cpu_cuda_fallback_layers`. `NVFP4_CPU=1` разрешает CPU W4A4
реализацию Blackwell MMQ с отдельными внешними масштабами; до успешного
полномодельного gate это диагностический вариант. Его микропроверка не
заменяет проверку routing, KV и logits всей модели.

CUDA-совместимый CPU executor использует существующий постоянный ggml pool.
Размеры буферов, маршруты, масштабы и конечность значений проверяются перед
вычислением и при получении матричных результатов. Ошибки внутри worker
сохраняются локально; все workers проходят оставшиеся барьеры, после чего
вызывающий поток получает исключение. Так исключение не оставляет остальные
потоки ждать барьер. В full CPU rank reduction выполняется в этом же pool,
в исходном порядке top-k. `cpu_reduce_ms` уже включено в `cpu_compute_ms`.

В hybrid решение принимается для целого эксперта на слое. Число назначенных
токенов и исходный объём весов определяют цену. Уже резидентные эксперты
считаются на GPU без новой загрузки. Для холодных экспертов модель выбирает
перенос на CPU, если это уменьшает максимум оценок CPU и GPU полос. CPU worker
и DMA/GPU могут работать одновременно. Слияние возвращает вклады в исходном
порядке top-k; численный результат проверяется отдельным oracle gate.

`UPLOAD_WINDOW=1` делает checkpoint после каждого реально загружаемого
холодного эксперта; резидентные эксперты в это окно не входят. Это ограничивает
очередь копирований, чтобы маленькие CUDA quant/OAI вызовы не ждали весь
слоевой поток весов. `DEVICE_GATHER=1` использует исходный GPU normalized
tensor и `get_rows`; на GPU передаются индексы, а не host-дубликаты F32 строк.
Оба параметра меняют планирование/перенос, а не выбранные expert IDs или веса.

Если GPU-полоса получила от1 до8 реальных route rows, её matmul дополняется до9
строк копиями последнего реального route/input/slot, чтобы native backend
сохранил MMQ вместо MMVQ. Выходы дополнительных строк пишутся в отдельный
dummy-хвост scratch и исключаются из исходного top-k суммирования.
Без этого короткая GPU-полоса меняет формат квантования
относительно полного GPU oracle. Проверены и host gather, и device gather:
в targeted resident-cache code128 gate оба варианта совпали с oracle побитно,
а профиль подтвердил реальные полосы из7 и6 строк с padding2/3.

## Воспроизведение измерений

GPU запускается только через собственный aictl-пресет и card lock.
`shortprefill_prepare.py` создаёт планы и jobs, **не запускает GPU**:

```bash
python3 tools/m31/shortprefill_prepare.py \
  --out /mnt/ai/logs/m31-vision/shortprefill/prepared-NEW \
  --engine /ABS/FROZEN/m31_shortprefill_bench
```

Сначала запускают `shortprefill-quick-gate-v1.json`: code128, off/CPU,
численная проверка против принятого PR GPU-offload oracle. Затем
`shortprefill-quick-sweep-v1.json`: n=16/128/515. Полная матрица `wide` включает
n=16…2048 и добавление 100/300 новых токенов к KV-префиксу515. Текст515 взят из
сохранённого natural-text запроса предыдущего TTFT-теста. Для gates текст515 и
code3000 отдельно создаются новые full-row oracle с одним полным префиллом.
`gate` также включает ref PNG/video. `long` проверяет 4K/16K/32K в контексте40K.

Сборки выполняются с `-j24` под shared
`/mnt/ai/logs/m31-port/.build.lock`. Скоростной job держит exclusive этот lock
в течение всей сессии. Долгий запуск передают `vision_card_launch.py`, который
использует systemd, собственный пресет с резервной копией и откатом. Каждый
basename job должен быть новым; повторное использование старого результата
отклоняется. Не запускайте сессию, владеющую чужим пресетом.

```bash
python3 tools/m31/vision_card_launch.py \
  /ABS/prepared-NEW/shortprefill-quick-gate-v1.json \
  --unit codex-m31-vision-shortprefill-quick-NEW
```

Нативный benchmark инициализирует один Engine. KV сбрасывается перед каждым
образцом; expert LRU и route history сохраняются. Порядок режимов вращается
между повторами; warmup сохраняется отдельно и исключается из медиан. При
измерении нового suffix реальный префикс заново считается в `off`, затем
время только новых токенов и last-row head записывается отдельно. Whole-prompt
checkpoint/cache в этих замерах не используется.

Изменение резидентности видно в дельтах upload/hit counters. CPU demand bytes
обозначает сумму выбранных весов один раз на слой/эксперт; это **не замер
фактического DRAM-трафика**. CPU/GPU длительности могут перекрываться; их нельзя
складывать и выдавать за wall time. Подробный per-layer trace лучше снимать
отдельным диагностическим образцом.

```bash
python3 tools/m31/shortprefill_summarize.py \
  /ABS/quick-sweep-v1/summary.json \
  --out /ABS/quick-sweep-v1/aggregate
```

Агрегатор пишет JSON и Markdown с медианами, фактическими chunks, счётчиками
и выигравшими проверенными точками. Native TTFT здесь не включает HTTP,
декодирование медиа, encoder, reasoning или первый decode step. Для итоговой
цели `<1 с` нужен дополнительный HTTP same-request замер с
`cache_prompt:false`, warm encoder и прежним vision/tools quality gate.

## Проверка корректности

Full-row gate читает accepted oracle напрямую и не создаёт ещё один
многогигабайтный logits-дамп. Проверяются canonical model path, token IDs,
позиция0, одинаковый одночанковый рецепт и полный, необрезанный head. Oracle
обязан иметь `backend=cuda`, `oracle_op_offload=true`, F16 KV и полный последний
слой модели до head. Старый oracle с другой нарезкой или decode tail не
доказывает побитность этого префилла.

В receipt отдельно записываются совпадения строк/значений побитно, top-1,
mean KL(oracle||candidate), max KL и max absolute drift. Численный допуск
explicit в prepared plan: top-1≥99%, mean KL≤1e-3, max KL≤0,05. Нельзя объявлять
побитность только по прохождению этих допусков. Для строгой проверки задают
`"gate": {"bitwise": true}`.

Синтетические CPU tests: `m31_shortprefill_policy_test`,
`m31_shortprefill_cost_test`, `m31_shortprefill_cpu_executor_test` и
`m31_shortprefill_cpu_lane_test`, а также
`m31_shortprefill_cuda_math_cpu_test`, `m31_shortprefill_cuda_executor_test`,
`m31_shortprefill_cuda_nvfp4_cpu_test`. Assert-based targets должны собираться с
отменой `NDEBUG` даже в Release. `shortprefill_test_harness.py` проверяет
агрегацию без модели/GPU.

Одинаковые single-expert входы отдельно проверяет диагностический helper:

```bash
# Только внутри собственного aictl-owned card job.
m31_expert_check --model /ABS/model.gguf --out /ABS/NEW-DIR \
  --short-cpu-check 1 --short-cpu-math both --threads 80 --raw 0
python3 tools/m31/shortprefill_math_summarize.py /ABS/NEW-DIR/report.json \
  --out /ABS/NEW-DIR/summary-n16-n128
```

Он не создаёт RAM-арену модели: читает исходные веса одного эксперта. По
умолчанию проверяет слои3/10/52 и n1/7/8/16/128; эталон — native
`cuda_id_auto`. Для n≤8 native CUDA может выбрать MMVQ, а сравниваемый CPU
diagnostic MMQ использует другой формат. Сводка n16/n128 сохраняет raw и
scaled gate/up/down, OAI и ошибки отдельно. Ни она, ни успешные CPU tests не
являются подтверждением цели TTFT<1с или полномодельного numerical gate.
