# Port7: ограниченное ожидание MONITORX/MWAITX

Это отдельный резерв для ожидания **между** заданиями CPU pool. Vendor, Engine, барьеры и default polling не менялись. Сборка standalone v2 прошла rc0 за1.437с; ELF `build-port7-cpu-mwaitx/v2/port7_cpu_mwaitx_probe` SHA174b2b72, source SHAf19e0a60 до/после равны. Failedv1 завершилась до компиляции из-за отсутствовавшего parent directory, log сохранён. Затем standalone check выполнен в согласованном clean CPU окне: PASS38arms за1.506с, feature действительно использована и forced fallback проверен. Флаг `mwaitx` есть в `/proc/cpuinfo` этого EPYC9654, но это не заменяет runtime proof.

Первичный AMD APM24594r3.34, печатные страницы232/258–259, разрешает обе инструкции на CPL3 независимо от MSR MonMwaitUserEn. Feature — CPUID80000001.ECX29. MONITORX требует ECX0; MWAITX ECX2 включает таймер EBX в TSC/P0 clocks, причём EBX0 **отключает** таймер. После MONITORX надо повторно проверить условие; после любого возврата проверить снова: причина выхода не сообщается. [Руководство AMD, зеркало оригинального PDF](https://kib.kiev.ua/x86docs/AMD/AMD64/24594_APM_v3-r3.34.pdf).

Локальный Linux7.0.0-34 `arch/x86/include/asm/mwait.h` подтверждает timer-enable bit1, SW P0=TSC и C0 hint0xf0. EAX0 просит C1. Поэтому первый кандидат — C0: отсутствие C-state перехода оставляет шанс на короткий wake, но экономия энергии не гарантирована. [Первичный kernel source](https://raw.githubusercontent.com/torvalds/linux/master/arch/x86/include/asm/mwait.h). Сам Linux использует `MWAITX_DISABLE_CSTATES` в [delay_halt_mwaitx](https://raw.githubusercontent.com/torvalds/linux/master/arch/x86/lib/delay.c), чтобы уменьшить wake latency; комментарий говорит0xf, но фактический macro —0xf0, согласованный с AMD EAX[7:4]. Kernel delay не является proof userspace pool или межъядерного wake.

Локальный GCC14 `mwaitxintrin.h` даёт `_mm_monitorx(pointer,extensions,hints)` и `_mm_mwaitx(extensions,hints,clocks)`: второй вызов использует порядок ECX,EAX,EBX. Он отличается от kernel helper `__mwaitx(eax,ebx,ecx)`. Target-атрибут изолирует инструкции; detector и fallback компилируются без `-mmwaitx`/`-march=native`. Общую рекомендацию GCC разделять detection и ISA код см. [GCC x86 built-ins](https://gcc.gnu.org/onlinedocs/gcc/x86-Built-in-Functions.html).

`tools/m31/port7_cpu_mwaitx_proposal.cpp` — маленький независимый ping-pong. CPUID проверяется до первой инструкции; до создания потоков fork-child выполняет один bounded wait на собственной валидной cacheline. SIGILL, Linux SIGSEGV при #GP, alarm и родительский deadline дают отказ capability и PAUSE fallback, не устанавливая глобальный SIGILL handler в threaded Engine. Forced fallback также явный. Этот startup fork нельзя бездумно переносить в уже запущенный Python/HTTP process: production capability-probe должен произойти до pool или в отдельном exec helper.

Порядок протокола: acquire condition → MONITORX → acquire condition → bounded MWAITX → снова condition. Оба release/acquire для публикации данных сохраняются; MWAITX не заменяет memory ordering. Изолированные generation/ack cachelines живут до join. Публикуемый timestamp — отдельная atomic запись перед release generation; метрика включает timestamp и coherence cost. Не утверждается чистая аппаратная wake latency.

Предлагаемое первое окно: один CXX build через shared build lock; затем отдельный CPU-only check≤15с с внешним timeout. PAUSE/C0/C1 в чередующемся порядке, sender/waiter на двух разных физических cores (оба sameCCD и differentCCD), gaps0/5/50µs, 1000–10000 итераций, bounded clocks≈2/10µs после измерения TSC frequency. Все clocks>0; duration и deadline контролировать монотонными часами. Поля результата: режим и effective fallback, CPUID/probe status, p50/p95/p99 publish→observe, число waits/миграций, elapsed. Нужны также cases write-before-arm и timeout-with-no-writer: текущий ping-pong покрывает возможную гонку, но не доказывает каждый schedule; их добавить перед production proof. Не называть `clocks` количеством CPU boost cycles.

Следующий proof только при хорошем результате: 79 ожидающих workers + producer, все читают один generation, каждый подтверждает работу отдельной cacheline; это обнаружит herd/coherence/CCD penalty, которого нет у двух потоков. При старте pool состояние stop/pause проверяется вместе с generation: текущий `ggml_graph_compute_thread_ready()` зависит от всех трёх. MONITORX только на `n_graph` не заметит stop/pause другого cacheline, поэтому таймаут должен возвращать к полной ready-проверке. Сохранить существующий post-poll synchronization. Внутренние FFN barriers не изменять.

Энергия: на узле есть `/sys/class/powercap/intel-rapl:0`, name=`package-0`, max_energy_range_uj=65532610987. Однако energy_uj имеет mode0400 root:root и **недоступен User=nekto** (проверено test-r без чтения privileged counter). Поэтому текущий proposal измеряет лишь wake/throughput; power proof отсутствует. Никаких MSR/sysctl/permissions изменений. Thread CPU time может остаться высоким, потому что аппаратное ожидание не обязано дескедулить поток; падение sampled cycles само по себе не измеряет watts. Если позже появится отдельно разрешённый читаемый counter, надо проверить wrap-around и одинаковый wall интервал; background miner и другие процессы исключают сильное package-energy утверждение.

Имеющиеся54.4% sampled userspace cycles в outer poll+barrier **не равны** доле wall time. Outer wait перекрывается с GPU, а measured POLL0 ухудшал компонент. Даже отличный micro wake не доказывает прирост TG. Для перехода в opt-in нужны сначала fallback/race/79-worker proof, затем отдельные component bitchecks и paired model TG/PP/quality на одинаковой финальной сборке. При длинном C1 wake или проигрыше C0 PAUSE идея отклоняется.

Итог выполненного tiny check: PAUSE/C0/C1 median p50 wake sameCCD85/305.5/305ns, differentCCD240/346/341ns. MWAITX здесь медленнее; energy/79worker/model proof отсутствуют.
