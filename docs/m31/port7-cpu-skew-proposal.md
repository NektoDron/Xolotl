# Port7: приватная instrumentation для CPU work skew

Подготовлен private fork frozen CPU component в `build-port7-cpu-skew-proposal/v1/`: `proposal.json` фиксирует каждый SHA и исходный `CpuFusedDecode` SHA6bc92628. Production header/Engine/веса не менялись. Генератор — `tools/m31/port7_cpu_skew_prepare.py`, logger — `port7_cpu_stage_trace.hpp`. Сборка v2 завершилась rc0: `build-port7-cpu-skew/v2/port7_cpu_skew_replay`, manifest `build.sha256`; v1 не прошла до компиляции из-за отсутствовавшего frozen `m31_geometry.hpp`, исправлено добавлением исходного frozenV7 файла. Replay затем выполнен в разрешённом clean CPU окне: `port7-cpu-skew-check-v1/receipt.json`, rc0/PASS за4.328с,3840 token-FFN rows побитно. Ожидание X-lock чужой vision сборки было до начала replay таймера; модельная скорость не измерялась.

Используется прежний actual-route CPU replay (5 реальных IQ3/IQ4/NVFP4 слоёв,8×127 маршрутов, синтетические одинаковые входы). Меняется только private default-mode0 `CpuFusedDecode`: per-thread begin/work-end/barrier-exit timestamps для input quant, GU, OAI, down quant, down и rank sum; worker row count, GU/down begin/end CPU IDs. Worker records выровнены по cacheline, нет timestamp atomics. Commit выполняется на main после synchronized graph compute и копирует только агрегаты. Прежнее побитовое serial-vs-grouped сравнение остаётся.

Нужны median и p95 отношения max work / mean work внутри каждого GU/down pass, p95 work / p50 work, barrier wait отдельно от useful work, постоянные tail worker/core и миграции. Quant phases отдельно показывают отсутствие useful work у79/76 workers; их нельзя смешать с GU/down skew. Framework entry/exit barriers и idle pool polling не измеряются этими custom-op stamps. Clock-call overhead не калиброван; это instrumentation, не новый throughput benchmark. Прежние serial_s/speedup из replay загрязнены commit/aggregation и должны игнорироваться.

Только после фактов можно выбирать scheduler:

- Если GU/down work max/mean близок1.0, dynamic assignment не лечит основную задержку; barrier/poll issue отдельно.
- Если существенный устойчивый work tail привязан к отдельным CPUs/миграциям, сначала рассмотреть выделенные physical cores и driver/helper CPUs. Нельзя заключать по16% sampled barrier cycles, что16% wall устранимы.
- Dynamic chunk32/64 сохраняет каждый dot и original-rank sum, но на24576rows даст≈768/384 успешных fetch_add плюс около80 terminal claims на фазу. Единый контended atomic пересылает cacheline между CCD; гипотетические50–100ns наclaim дают≈23–85µs/phase — возможная заметная цена против сотенµs полезной работы. Это оценка, не microbench.
- Block-cyclic32/64 не требует atomics и распределяет данные по workers, но ухудшает последовательный prefetch между chunks и сам вводит до одного chunk разницы в числе rows. Обычный cyclic-by-row имеет большой stride и ещё хуже локальность. Без существенного measured skew это может проиграть нынешним contiguous ranges с разницей≤1row.

Сборка выполнена после V9 build в разрешённом слоте validation; replay только в отдельном clean CPU окне. GPU в этом компоненте нет, поэтому модельный driver/GPU-helper contention сюда автоматически не переносится. Новые scheduler production opt-ins пока не реализованы.

## Полученный skew

Полный небольшой анализ — `/mnt/ai/logs/m31-port/port7-cpu-skew-analysis-v1.json`. Во всех GU/down80 workers имеют307–308 rows, разница counts≤0.33%. Однако median max-work/mean-work по5 слоям: GU1.180–1.214, down1.206–1.302; p95 этих ratios достигает1.87/1.99. Median GU mean206–216µs и max244–264µs, down mean110–138µs и max135–174µs. Median barrier mean wait GU39–48µs/down25–36µs согласован с work tail. Это измеренный phase skew, не доля устранимого wall Engine.

Last placement показывает79 physical cores на80 workers: workers12/32 сидят на подтверждённых sysfs SMT siblings144/48, и они имеют максимальные средние useful work в GU/down. Их L3id3 содержит9 workers, L3id9 не представлен. Это last snapshot, не continuous affinity trace; внутри GU/down миграций мало, но переходы между фазами не посчитаны. Некоторые GU tail workers повторяются часто, down slow workers группируются в перегруженном L3. Поэтому есть сначала placement/locality гипотеза, а не ошибка floor partition. Прежний первый sweep со строгими spread/compact80 не ускорился; новый результат не отменяет его и не разрешает менять default pinning.

Inputquant active1 worker≈9.9µs, OAI80≈2.3µs, downquant4≈1.7µs, rank-sum80≈1.2µs (median across layers). Их idle/barrier ratios нельзя использовать как GU/down useful-work skew. Timestamp/barrier bookkeeping включён в записи; small-phase timing наиболее чувствителен к overhead.

Dynamic32 даёт768 успешных global claims на24576 rows плюс≤80 terminal; chunk≈22µs GU/12.5µs down при текущем среднем. Dynamic64 даёт384 claims, но chunk≈44/25µs, уже сопоставим с наблюдённым median tail: крупная гранулярность может съесть выигрыш. Прежняя оценка23–85µs serialized atomic service — лишь гипотетический диапазон; нельзя просто прибавлять его к wall, часть claims перекрывается со счётом других workers. Нужна собственная contention калибровка, если этот вариант продолжать.

Статический cyclic32/64 сам создаёт counts9/10 или4/5 chunks наworker, то есть≈11%/25% row-count range против нынешних0.33%; это плохой первый контроль. Cyclic8 ограничивает count range≈2.63%, но даёт≈38–39 коротких последовательных блоков вместо contiguous range и не лечит общий compute slowdown SMT core. Лучший следующий bounded контроль — тот же private instrumented replay со strict spread physical80, без новой сборки, чтобы узнать, исчезает ли tail; лишь затем private dynamic32 или cyclic8, если skew остаётся. Никакой новый scheduler пока не реализован или предложен для production default.

Root разрешил один такой strict контроль: подготовлен `port7_cpu_skew_spread_check.sh`, который читает actual allowed CPUs/sibling lists/L3 IDs и выбирает80 unique physical cores равномерно по12 L3, фиксируя topology.json. Тот же ELF/IDs/weights, никаких новых kernels/defaults. Контроль затем выполнен: PASS3840rows за4.250с,80physical/0SMTdups/0inphase migrations. GU max work−1.6..2.7%, down−3.4..+0.3%; tail сохранился. Полный comparison `port7-cpu-skew-spread-comparison-v1.json`, итог `docs/m31/port7-cpu-reserve-final.md`. Важное ограничение будущего model arm: ggml threadpool strict placement пинит также main thread на последний CPU. Engine создаёт pool до host.load и GpuExperts/GpuCpuQuants; helper threads без отдельной affinity наследуют текущую primary маску. Private CPU-only результат не проверит поздние GPU/loader helpers, которые могут оказаться на одном CPU. До model pin80 сравнения надо явно проверить их реальные /proc task masks или отдельную helper affinity. Это source finding, без изменения runtime.
