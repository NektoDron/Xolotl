## Port3: проверенный CPU path и диагностика GPU

Opt-in `--reuse-allocations1 --persistent-cpu-pool1 --cpu-residual1`
(в CLI имена и значения передаются отдельными argv) сохраняет ggml операции и
F32 порядок сложения. Gallocr и metadata workspace переиспользуются, но allocator
явно reserve/replan каждый transient graph: node counts недостаточно для проверки
alias topology. Большие MSA positions/mask/bias/cell-block inputs загружаются один
раз на chunk для всех60 слоёв. Persistent CPU pool отсоединяется от borrowed
backend перед освобождением. Default M1 путь не меняется.

CPU/CUDA builds + tiny1/7/29 — побитно с прежним путём. Настоящие code128 и
3000code/decode_tail32 — все3128 logits побитно с PR CPU-expert oracle:
`opt-code128-compare-v1.json`, `opt-decode-compare-v1.json`.

`m31_tokenizer` из PR: NFC, исходный template, reasoning/PEG nested XML tools.

### Почему первый GPU cache path не принят

Original-type LRU+pin staging+grouped per-expert matmul собран, но code128 gate
провалился: top1=.72656, meanKL=.87999 против CPU oracle. Q8 activation env даёт
.87637 и не исправляет проблему. Raw128 forward10.145s,5153misses/115.56GB upload;
это не benchmark. Исходный вариант сохранён в logs/m31-port/
`m31_gpu_experts-before-id-v1.{cpp,hpp}`.

`m31_expert_check` на оригинальных expert0 layers3/10/52 и n1/7/128:
CPU `mul_mat`/`mul_mat_id` побитны; CPU vsGPU full expert около1–1.6% relativeL2
уже без arena/cache/grouping. CPU IQ3/IQ4 dot использует Q8_K активации,
CUDA — Q8_1. Q8 env не меняет block scheme. NVFP4 n128 W4A4 даёт7.75%, Q8≈1.01%.
`expert-probe-v1/report.json`, raw layer10/n128 `expert-probe-raw-v1`.

Добавлен отдельный `m31_oracle --oracle-op-offload1` диагностический режим;
M1 default false сохранён. GPU-offload oracle vsCPU oracle тоже расходится:
top1=.78125, meanKL=.77857. Native grouped vsGPU oracle всё ещё не проходит:
top1=.734375,meanKL=.73508. Нельзя назвать первый вариант эквивалентным даже
GPU placement. Layers0..2 и ffn_norm/shared слоя3 побитны; первыйdiff l_out3
relativeL2=4.09e-5; далее накапливается. Это локализовано в routed MoE3.

Причина дополнительного округления: grouped эксперт часто видит<=8 токенов и
выбирает MMVQ сF16 scale, oracleID128 — MMQ сF32 scale для IQ3/IQ4.
Raw probe CUDAmm128 vsCUDAid128: single matrix relL2≈2.7e-7, full≈1.04e-4.
Следующая реализация в работе — fixed VRAM slots и единый layer `mul_mat_id`
с исходным n/used и remapped expert IDs, без изменения типа/байтов весов.
Для GPU byte stride должен делиться на размеры block98/136/36 и backend alignment;
простого128byte alignment недостаточно.

## Предыдущая проверенная RAM-арена

Реализован изолированный opt-in `--arena-gib170` только в `tools/m31`.
`m31_arena.hpp` пакует каждого из7296 экспертов в RAM как
`[gate|up|down|NVFP4-scale-tail|alignment]`, без requant и изменения маршрутов.
CPU ggml tensor views используют этот expert stride, сохраняя исходные типы;
исходные GGUF не меняются. Gate/up/down source stride вычисляется из row size,
а16-byte scale tail добавляется отдельно. На NVFP4 down52/58/59 хранятся
{1,1,s_down,0}; исходные `.scale` также остаются доступны CPU graph.

Арена пока **pageable**, без pinned DMA и VRAM-кеша. Это подготовка к тирингу,
не ускоренный MoE path и не реализация сервера. Бюджет должен вмещать все routed
weights; оставляется16GiB MemAvailable. По умолчанию0 — старый mmap-путь.
Внешний CPU scratch общего Ds4MoeTier не используется: пока работает проверенный
ggml CPU routed path с OAI и динамическими buffers.

Проверки:

- CPU и CUDA сборки rc0; логи build-cpu-20261026T180120Z.log и
  build-cuda-20261026T180128Z.log.
- Tiny NumPy chunk1/7/29 maxabs0.00011285; comparator4/4 и loader negatives.
- Tiny arena/mmap logits побитно одинаковы; недостаточный бюджет отклоняется.
- Реальный GGUF, code128, --arena-gib170:7296 экспертов,
  **163754029056 байт (152.51GiB)**, pack73.160с. Все128 logits побитно
  совпали с PR oracle (top1=1/KL0/maxabs0), включая слои с NVFP4.
  `arena-compare-v1.json`, job-arena-v1*. Unit/job rc0, cleanup выполнен.
  Весь pack/inference через systemd-run/aictl, GPU0, lock/trap, nofusion.

Осталось для M2:

1. Pinned arena/DMA и VRAM-cache отдельных экспертов; копировать исходные blob bytes,
   не менять маршрутизацию. Использовать Layer/Slice descriptors арены.
2. Layer-batched grouped GPU prefill с переиспользованием экспертов по всем токенам;
   persistent graphs и CPU pool вместо transient graph/allocation на каждом шаге.
3. Если подключать общий Ds4MoeTier: OAI alpha1.702/limit7/up+1 во ВСЕХ его
   CPU/CUDA/grouped/MMQ путях; scratch>=7008/3504/3072; внешний NVFP4 scale и
   правильный down source stride. Нынешний Ds4GgufBlobs нельзя применять как есть.
   Паддинг арены не является частью blob payload, и её stride не равен старому
   contiguous tensor stride. Альтернатива первой интеграции — проверенные ggml ops
   на cached GPU blobs, до замены вычислительных kernels.
4. OpenAI server, свой NFC tokenizer/chat/think/stop/tool streaming parser.
5. Свой тестовый preset m31-xolotl, с backup/rollback. Текущий batch preset после
   каждой проверки снимается, постоянного server preset сейчас нет.
6. om_bench.py TG4K/16K/32K, PP4K/32K; GSM8K100/tools23. Сравнивать с лучшим
   1GPU ref23.33/22.63/21.92TG и425/433PP (q8_0/64K/ubatch2048/op_offload on).
   M1 oracle nofusion/op_offload=false — эталон математики, не speed-плечо.

CUDA fusion сейчас должна оставаться выключенной в M1-конфигурации ОБОИХ
процессов; exact fused operation пока не локализована. Не включать оптимизацию
без raw-logits/quality regression gate. M3/M4 ещё не начаты. Критерий остановки
после слабого выигрыша M2 ещё не применялся: M2 benchmark не проводился.
