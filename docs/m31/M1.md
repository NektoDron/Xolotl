## Конфигурация и воспроизведение

- Xolotl branch `aiserver/m31-port`, HEAD `cd4cc85c726448a6a90d9cb85475fd95e777aeea` плюс незакоммиченный M1 patch. Точные source hashes/patch: `/mnt/ai/logs/m31-port/suite20-v1-source.{json,patch}`.
- Golden binaries сохранены: `/mnt/ai/logs/m31-port/m31_generate-m1` и `m31_oracle-m1`.
- Oracle отдельно связан с STATIC libraries PR31192 SHA6b95a990. Исходники PR не изменялись.
- Те же пять NVMe UD-IQ3_S исходной HF revision02c81e4, проверенные ref-агентом; никаких requant/route bias/skip/prune.

- ОБА процесса: GGML_CUDA_DISABLE_FUSION=1. Включённая fusion не проходит корректность в этой конфигурации; точная fused operation пока не локализована. Это ограничение принятого M1, а не speed-настройка референса M2.

## Существенные исправления

1. F16 index cache переводится в F32 перед dot, как PR get_rows.
2. Main/index KV window padding>=256, как PR. Pad128 менял FA kernel/tiling; на128-token chunk небольшая attention error усиливалась по60 слоям.
3. CPU FA получает F32 V с исходными F16 cache values, чтобы накопитель не округлялся после каждого key. CUDA F16 caches сохранены.
4. Head одним chunk, как oracle: MMV и MMQ имеют разное activation rounding.
5. Oracle taps различают промежуточный и post-RoPE Qcur/Kcur, пропускают copy names; ошибка capture не обрывает один scheduler split. Все60 l_out на64RU в диагностике совпали побитно.
6. Попытка заменить bare gallocr на scheduler не устранила fusion discrepancy и отменена.
